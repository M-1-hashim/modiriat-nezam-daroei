# نظام مدیریت دارویی — نسخه حرفه‌ای 🇦🇫

سیستم جامع، حرفه‌ای و production-ready برای **شرکت‌های واردات و عمده‌فروشی ادویه (دارو) در افغانستان** — ساخته‌شده بر اساس لوجیک واقعی تجارت دارویی بازار افغانستان.

> ⚙️ **استک:** Next.js 16 (App Router) + TypeScript + Tailwind CSS 4 + shadcn/ui + Prisma (SQLite — قابل تبدیل به MySQL)
> 🖥️ **رابط:** دری افغانستان، راست‌به‌چپ (RTL)، تقویم هجری شمسی افغانی (حمل، ثور، جوزا...)، منطقه زمانی کابل (UTC+4:30)
> 📴 **حالت:** آنلاین + **آفلاین واقعی** با همگام‌سازی خودکار، PWA

## ۱. قابلیت‌ها

### تجارت
- **خرید** (محلی / وارداتی / خارجی): فاکتور با بچ، تاریخ تولید و انقضا، **تعداد مجانی (پروموشن)**، تخفیف درصدی/مبلغی، مصارف اضافی (ترانسپورت، گمرک) با توزیع خودکار، اسعار چندگانه (AFN/USD/PKR) با نرخ ذخیره‌شده در هر سند
- **بهای مؤثر خودکار:** مثال — ۱۰۰ عدد پرداختی + ۱۰ مجانی به ۹٬۰۰۰ افغانی → بهای هر واحد = ۸۱٫۸۲ افغانی (شامل تعداد مجانی و مصارف اضافی)
- **فروش** (عمده / نقدی / قرضی): انتخاب بچ از موجودی زنده، کنترول انقضا، **سقف اعتبار مشتری**، تعداد مجانی پروموشنی که موجودی را زیاد می‌کند ولی مبلغ مشتری را نه
- **پرداخت‌ها:** دریافت از مشتری / پرداخت به تأمین‌کننده، پرداخت جزئی، پیش‌پرداخت، رسید چاپی
- **برگشتی‌ها:** برگشت جزئی/کامل فروش و خرید با اثر خودکار بر موجودی، بچ، توازن و منفعت
- **مشتریان:** فارمسی، شفاخانه، کلینیک، شرکت — با منطقه، فروشنده، سقف اعتبار، شرایط پرداخت، صورت‌حساب چاپی
- **تأمین‌کنندگان:** داخلی و خارجی با توازن بدهی

### انبار
- **گدام‌های متعدد** در هر شعبه، موجودی **سطح بچ**
- **ردیابی کامل بچ:** از کدام خرید/تأمین‌کننده آمده، چه حرکاتی داشته، به کدام مشتریان فروخته شده، الان کجاست
- انتقال بین گدام‌ها، تعدیل موجودی، خسارت و خراج منقضی — همه با سابقهٔ حرکات (Stock Movement)
- هشدارهای انقضا (قابل تنظیم: پیش‌فرض ۹۰ روز) و کمبود موجودی

### مالی و حسابداری
- **زنجیرهٔ مالی شفاف:** عواید ← بهای تمام‌شده (COGS تاریخی از `costAtSale`) ← منفعت ناخالص ← مصارف ← **منفعت خالص** ← توزیع
- **مصارف شعبه** با کتگوری، تأیید و وضعیت
- **شراکت سهامی** (درصد سهام، سرمایه، سهم منفعت/زیان) و **مضاربه** (تأمین‌کنندهٔ سرمایه / شریک کارگر) — جدا از هم، مطابق قرارداد واقعی
- **توزیع منفعت** برای دورهٔ انتخابی با پایهٔ قابل تنظیم (منفعت خالص / ناخالص / عواید) — هیچ فورمول ثابت hard-code نشده
- **اسعار:** AFN ↔ USD ↔ PKR با نرخ خرید/فروش، به‌روزرسانی از API قابل تنظیم، ثبت دستی با نام کاربر، **نرخ هر سند در همان سند ذخیره می‌شود** و هرگز با نرخ روز بازمحاسبه نمی‌شود

### مدیریت
- **چند-شعبه‌ای واقعی:** شعبه ← گدام ← مشتری ← فروش ← مصرف ← شراکت — هر رکورد به شعبه‌اش مقید است
- **امنیت شعبه‌ای در بک‌اند:** کاربر شعبه‌ای هرگز با تغییر URL/id/API به شعبه دیگر راه ندارد (انفورس در همه APIها)
- **رول و صلاحیت** قابل تعریف: ۱۹ ماژول × ۵ اکشن (دیدن/ایجاد/ویرایش/حذف/تصویب)
- **جریان تصویب قابل تنظیم** برای خرید، فروش، مصارف و برگشتی‌ها
- **سابقهٔ فعالیت (Audit Log)** با مقدار قبل/بعد برای هر تغییر مهم
- **نسخه‌های احتیاطی** و بازیابی کامل
- **راپورها:** فروش/خرید (روزانه، ماهانه، شعبه، مشتری، فروشنده، منطقه، محصول، بچ)، موجودی/ارزش‌گذاری/انقضا، مالی، اسعار — با خروجی CSV و چاپ
- **داشبورد** نقش-محور برای دفتر مرکزی و مدیر شعبه
- **جستجوی سراسری** (Ctrl+K): محصول، بچ، مشتری، فاکتور، رسید
- **PWA + آفلاین واقعی:** در قطع انترنت، اسناد به‌صورت محلی با شناسهٔ یکتا (UUID) ذخیره و پس از اتصال **خودکار و idempotent** همگام می‌شوند

## ۲. نصب و اجرای محلی

پیش‌نیاز: [Node.js 20+](https://nodejs.org) یا [Bun](https://bun.sh)

```bash
# ۱) نصب پکیج‌ها
bun install        # یا: npm install

# ۲) تنظیم متغیر محیط
echo 'DATABASE_URL=file:/absolute/path/to/db/custom.db' > .env

# ۳) ساخت جدول‌های دیتابیس
bun run db:push    # یا: npm run db:push

# ۴) اجرای سرور توسعه
bun run dev        # یا: npm run dev
```

سیستم روی `http://localhost:3000` اجرا می‌شود. در اولین بازدید، **راه‌اندازی اولیه خودکار** انجام می‌شود (رول‌ها، شعبهٔ دفتر مرکزی کابل، گدام اصلی، کاربر admin، تنظیمات پیش‌فرض، اسعار اولیه).

### متغیرهای محیط (`.env`)

| متغیر | توضیح | مثال |
|---|---|---|
| `DATABASE_URL` | مسیر فایل SQLite (یا رشتهٔ MySQL در پروداکشن) | `file:./db/custom.db` |
| `NODE_ENV` | محیط اجرا | `production` |

## ۳. ورود اولیه

| نام کاربری | رمز | نقش |
|---|---|---|
| `admin` | `admin123` | مدیر ارشد سیستم (دفتر مرکزی) |

> ⚠️ **بلافاصله پس از اولین ورود، رمز admin را تغییر دهید:** کاربران و شعبه‌ها ← ویرایش admin ← رمز جدید. این حساب برای نصب و مدیریت سیستم است.

رول‌های پیش‌فرض: مدیر شعبه، حسابدار، فروشنده، مسئول گدام، مسئول خرید — همه قابل ویرایش‌اند و می‌توانید رول دلخواه با صلاحیت‌های دقیق بسازید (ماژول × اکشن).

## ۴. دیتای نمایشی (دمو)

در **تنظیمات ← دیتای نمایشی**، مدیر ارشد می‌تواند دیتای دمو را بارگذاری کند:
- شعبه‌های مزار شریف، هرات، قندهار + مناطق و فروشندگان
- ۱۲ قلم ادویهٔ واقعی بازار، ۳ تأمین‌کننده، ۸ مشتری
- ۱ خرید وارداتی (USD با نرخ ۷۲، تعداد مجانی، مصارف گمرکی)، ۳ فاکتور فروش (نقدی و قرضی با بدهی)، پرداخت‌ها، مصارف

دیتای دمو با فلگ `demo_data_loaded` از دیتای واقعی جدا می‌شود و فقط با دکمهٔ صریح بارگذاری می‌گردد — **هرگز در نصب پروداکشن خودکار ایجاد نمی‌شود.**

## ۵. تنظیمات اسعار

ماژول **اسعار** ← تنظیمات:
- **آدرس API:** پیش‌فرض `https://open.er-api.com/v6/latest/USD` (رایگان، بدون کلید). می‌توانید آدرس هر منبع دیگر — از جمله سرویس‌های مربوط به نرخ‌های **سرای شهزاده** — را وارد کنید؛ سیستم هیچ endpoint جعلی hard-code نکرده و دقیقاً همان آدرسی را صدا می‌زند که شما تعیین می‌کنید.
- **کلید API (اختیاری)**، **بازهٔ به‌روزرسانی (دقیقه)**، **تشهٔ فیلدها (mapping JSON)**: مثل `{"USD/AFN":"rates.AFN","USD/PKR":"rates.PKR"}` — مسیر فیلد نرخ در پاسخ JSON.
- **ثبت نرخ دستی:** کاربر مجاز می‌تواند نرخ خرید/فروش دستی ثبت کند؛ نام ثبت‌کننده و زمان ذخیره می‌شود.
- اگر API در دسترس نباشد، سیستم **آخرین نرخ معتبر ذخیره‌شده** را با برچسب «ذخیره‌شده/آفلاین» استفاده می‌کند و هرگز کار را متوقف نمی‌کند.
- نرخ لحظهٔ هر خرید/فروش/پرداخت در همان سند ذخیره می‌شود؛ تغییر نرخ روز، اسناد تاریخی را تغییر نمی‌دهد.

## ۶. نصب برای پروداکشن

```bash
# ۱) build
bun run build      # یا: npm run build

# ۲) اجرا
bun run start      # یا: npm run start
# سرور روی پورت 3000 بالا می‌آید (با Nginx/Apache reverse-proxy کنید)
```

### با Nginx (پیشنهادی)

```nginx
server {
    listen 443 ssl;
    server_name pharma.example.af;
    # ssl_certificate ...
    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-Proto https;
    }
}
```

### اجرای دائمی با systemd

```ini
# /etc/systemd/system/pharma.service
[Unit]
Description=Pharma Management System
After=network.target

[Service]
WorkingDirectory=/opt/pharma
ExecStart=/usr/bin/bun /opt/pharma/.next/standalone/server.js
Restart=always
Environment=NODE_ENV=production
Environment=DATABASE_URL=file:/opt/pharma/db/custom.db

[Install]
WantedBy=multi-user.target
```

### تبدیل به MySQL (اختیاری اما ساده)

در `prisma/schema.prisma` فقط یک خط تغییر می‌کند:

```prisma
datasource db {
  provider = "mysql"          // sqlite → mysql
  url      = env("DATABASE_URL")
}
```

و `DATABASE_URL=mysql://user:pass@host:3306/pharma` — سپس `bun run db:push`. کل کد و کوئری‌ها بدون تغییر کار می‌کند (Prisma دیتابیس را انتزاع می‌کند).

## ۷. هاست اشتراکی — معامله و راه‌حل

مشخصات پروژه، **هاست اشتراکی PHP/MySQL** را ترجیح داده اما صریحاً گفته: *«اگر انتخاب تکنولوژی با هاست اشتراکی تعارض داشت، معامله را توضیح بده و راه‌حل عملی انتخاب کن.»* معامله این است:

| نیاز | PHP اشتراکی | این سیستم (Node) |
|---|---|---|
| آفلاین واقعی + همگام‌سازی مطمئن | خیلی سخت (state سمت سرور ندارد) | ✅ کامل |
| امنیت شعبه‌ای در بک‌اند با تایپ سخت | دستی و خطاخیز | ✅ لایهٔ واحد |
| منطق مالی پیچیدهٔ قابل تست | — | ✅ TypeScript strict |
| قیمت/میزبانی ارزان | ✅ ارزان‌ترین | هاست Node ارزان (چند دالر در ماه) |

**راه‌حل‌های عملی به ترتیب ارجحیت:**

1. **هاست Node ارزان (توصیه‌شده):** هر هاستی که Node 20 بدهد (Cloudways، A2، Hostinger VPS کوچک، Railway، Render...) — طبق بخش ۶ نصب کنید. دیتابیس SQLite برای تک-سرور کافی و فوق‌العاده سریع است؛ برای چند-سرور همان یک خط provider را MySQL کنید.
2. **VPS کوچک + Docker اختیاری:** کنترل کامل، نسخه‌های احتیاطی خودکار با cron.
3. **هاست اشتراکی با cPanel «Setup Node.js App»:** برخی cPanelها (Alchemy/Node selector) اجرای Node را پشتیبانی می‌کنند — همان بخش ۶.
4. **هاست اشتراکی صرفاً PHP:** اگر *فقط* PHP موجود است، این پروژه اجرا نمی‌شود (Node لازم است). توصیهٔ صادقانه: هاست Node بگیرید یا این سیستم را روی یک VPS کوچک برای همهٔ شعبه‌ها میزبانی کنید — شعبه‌ها فقط از مرورگر/PWA استفاده می‌کنند و در قطع انترنت آفلاین کار کرده و بعداً همگام می‌شوند.

## ۸. نسخه‌های احتیاطی و بازیابی

- **ایجاد:** ماژول «نسخه‌های احتیاطی» ← «ایجاد نسخه احتیاطی» — کل فایل دیتابیس در `db/backups/` کپی و در سیستم ثبت می‌شود (نام فایل، حجم، تاریخ، یادداشت).
- **بازیابی:** مدیر ارشد ← دکمهٔ بازیابی ← تأیید صریح. ⚠️ بازیابی **تمام دیتای فعلی را با نسخهٔ انتخابی جایگزین می‌کند** — سیستم قبل از عملیات هشدار می‌دهد.
- **حذف:** نسخه‌های قدیمی را از همان صفحه حذف کنید (فایل + رکورد).
- **خارج از سیستم:** می‌توانید cron بگذارید که `db/custom.db` را کپی کند — فایل SQLite با فرمت استاندارد است.

```bash
# مثال cron: نسخه احتیاطی شبانه
0 2 * * * cp /opt/pharma/db/custom.db /opt/pharma/db/backups/auto-$(date +\%F).db
```

## ۹. کار با سیستم (راهنمای کاربر)

### ایجاد شعبه
مدیریت سیستم ← کاربران و شعبه‌ها ← تب «شعبه‌ها» ← «شعبه جدید» (کد مثل `JAL`، نام، شهر). سپس برای شعبه گدام، مناطق و کاربران بسازید.

### ایجاد کاربر
کاربران و شعبه‌ها ← تب «کاربران» ← «کاربر جدید»: نام، نام کاربری، رمز (۶+ کاراکتر)، رول، شعبه. کاربر شعبه‌ای **فقط** شعبهٔ خودش را می‌بیند — این محدودیت در سرور انفورس شده، نه فقط در ظاهر.

### رول سفارشی
تب «رول‌ها» ← «رول جدید» ← تیک صلاحیت‌ها (۱۹ ماژول × دیدن/ایجاد/ویرایش/حذف/تصویب) یا «دسترسی کامل».

### ثبت خرید وارداتی
خریدها ← «ثبت خرید جدید» ← تأمین‌کننده، گدام، نوع «وارداتی»، اسعار USD ← نرخ خودکار ← اقلام (محصول، شمارهٔ بچ، تاریخ تولید/انقضا هجری، تعداد، **تعداد مجانی**، قیمت، تخفیف) ← مصارف اضافی (ترانسپورت/گمرک) ← پرداخت ← «تأیید فوری». سیستم بچ‌ها را می‌سازد، موجودی (شامل مجانی) را وارد گدام می‌کند و بهای مؤثر هر واحد را حساب می‌کند.

### ثبت فروش
فروش‌ها ← «ثبت فروش جدید» ← مشتری (فروشنده و منطقه خودکار پر می‌شوند) ← گدام ← اقلام: محصول ← **بچ از موجودی زنده** (بچ منقضی غیرفعال است) ← تعداد/مجانی ← پرداخت. سقف اعتبار و موجودی زنده کنترول می‌شود.

### چاپ
هر فاکتور/رسید دکمهٔ چاپ با پیش‌نمایش دارد؛ دو تمپلیت ساده/مفصل (در تنظیمات یا هنگام ثبت). صورت‌حساب مشتری هم چاپ می‌شود.

## ۱۰. همگام‌سازی آفلاین

- وقتی انترنت قطع شود، هدر به حالت **آفلاین** می‌رود. ایجاد فاکتور فروش/خرید، پرداخت، مصرف و مشتری همچنان کار می‌کند و در `localStorage` دستگاه با **شناسهٔ یکتا (UUID)** صف می‌شود — دادهٔ وارد‌شده هرگز از بین نمی‌رود.
- با برگشت انترنت، صف **خودکار** (و با دکمهٔ همگام‌سازی دستی) به سرور ارسال می‌شود. نشانگر صف در هدر تعداد اسناد در انتظار را نشان می‌دهد.
- **جلوگیری از تکرار:** هر سند آفلاین `localId` یکتا دارد؛ ارسال دوباره هیچ‌وقت رکورد تکراری نمی‌سازد.
- **تعارض:** اگر مثلاً موجودی هنگام همگام‌سازی کافی نباشد، سند به وضعیت **CONFLICT/FAILED** می‌رود، در «لاگ همگام‌سازی» ثبت و به کاربر پیام داده می‌شود — داده بی‌صدا از بین نمی‌رود و overwrite نمی‌شود.
- محدودیت شعبه و رول در حالت آفلاین هم برقرار است (هم محلی، هم در سرور هنگام همگام‌سازی).

## ۱۱. امنیت

- رمزها با **scrypt + salt** هش می‌شوند (هرگز plain ذخیره نمی‌شوند)
- سشن با کوکی `httpOnly` + توکن هش‌شده در دیتابیس + انقضای ۳۰ روزه
- **صلاحیت و شعبه در همهٔ APIهای بک‌اند** چک می‌شود (نه فقط UI)
- کوئری‌های پارامتری Prisma → محفوظ از SQL Injection
- اعتبارسنجی همهٔ ورودی‌ها + پیام‌های خطای دری
- Audit Log برای هر عمل مهم (ورود/خروج/ایجاد/ویرایش/حذف/تصویب/پرداخت/بازیابی/تغییر نرخ...)
- سوئیچ HTTPS در پروداکشن (Nginx + Let's Encrypt)

## ۱۲. حل مشکلات

| مشکل | راه‌حل |
|---|---|
| صفحه خالی/خطای دیتابیس بعد از تغییر اسکیما | `bun run db:push` را اجرا و سرور را ری‌استارت کنید |
| «دریافت نرخ از انترنت ناموفق بود» | طبیعی است اگر API در دسترس نباشد — نرخ دستی ثبت کنید یا endpoint را در تنظیمات اسعار عوض کنید |
| اسناد آفلاین همگام نمی‌شوند | دکمهٔ همگام‌سازی در هدر را بزنید؛ پیام خطای هر آیتم در هدر/لاگ همگام‌سازی نمایش داده می‌شود (معمولاً موجودی ناکافی = تعارض) |
| فراموشی رمز admin | با دستور زیر رمز را ریست کنید: `cd project && bun -e "const{hashPassword}=require('./src/lib/auth');/* یا از /api/setup در حالت نصب تازه استفاده کنید */"` — ساده‌تر: رکورد User را از دیتابیس حذف و `/api/setup` را صدا بزنید تا admin پیش‌فرض دوباره ساخته شود |
| فونت دری لود نمی‌شود (بدون انترنت) | سیستم به Tahoma/Segoe fallback می‌کند؛ برای همیشه، فایل فونت Vazirmatn را لوکال میزبانی کنید |
| خطای «سقف اعتبار مشتری تجاوز می‌کند» | پرداخت از مشتری دریافت کنید یا سقف اعتبار را در پروفایل مشتری افزایش دهید |
| خطای «موجودی کافی نیست» | بچ درست را انتخاب کنید، انتقال بین گدام بزنید، یا خرید ثبت کنید |

## ۱۳. ساختار پروژه

```
├── prisma/schema.prisma          # اسکیمای کامل (۳۰+ مدل)
├── db/                           # دیتابیس SQLite + db/backups/
├── public/                       # manifest.webmanifest، sw.js (PWA)
├── src/
│   ├── app/
│   │   ├── page.tsx              # پوستهٔ SPA (لاگین، سایدبار، هدر، فوتر)
│   │   └── api/                  # ~۷۰ روت API (auth, purchases, sales, stock, reports...)
│   ├── components/
│   │   ├── shared/               # DataTable، FormDialog، چاپ، هدر و...
│   │   ├── ui/                   # shadcn/ui
│   │   └── views/                # ۱۹ ویو ماژول (داشبورد، خرید، فروش، ...)
│   └── lib/
│       ├── auth.ts               # سشن، هش، صلاحیت، انفورس شعبه
│       ├── business.ts           # موتور کسب‌وکار (موجودی، شماره‌گذاری، توازن، مالی)
│       ├── hijri.ts              # تقویم هجری شمسی افغانی
│       ├── client-api.ts         # لایهٔ API + صف آفلاین + همگام‌ساز
│       └── ...
└── CONTRACTS.md                  # قراردادهای فنی
```
